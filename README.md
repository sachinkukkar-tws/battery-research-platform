# Battery Research Platform

React frontend for the Battery Science proof of concept. People can explore ingested battery research papers, review the values extracted from them, compare anode and cathode materials, chart the findings, upload new PDFs and ask **Amplifi** questions about the papers.

It is a refactor of the single-file prototype `battery_platform_demo.html`. Every screen and workflow from the prototype has been kept; [docs/MIGRATION.md](docs/MIGRATION.md) maps each feature to its new home.

## Quick start

Requires Node.js 20 or later.

```bash
npm install
npm run dev          # http://localhost:5173, runs in mock mode with the bundled sample data
```

| Command | What it does |
| --- | --- |
| `npm run dev` | Development server with hot reload |
| `npm run build` | Typecheck, then production build into `dist/` |
| `npm run preview` | Serve the production build locally |
| `npm test` | Run the unit and integration tests once (`npm run test:watch` to watch) |
| `npm run lint` | ESLint, including the React rules-of-hooks checks |
| `npm run typecheck` | TypeScript only |
| `npm run build:standalone` | One self-contained HTML file in `dist-standalone/`, for sharing a demo like the original prototype |

## Mock mode and live mode

The app runs in one of two modes, set by `VITE_DATA_MODE`.

**Mock mode** (the default) uses the sample data from the prototype in `src/data/`. Nothing leaves the browser. Uploads simulate their pipeline steps, review decisions are kept for the session, and Ask Amplifi can answer only the four suggested questions. The UI says so everywhere it matters. The top bar shows *Demo data*. Every chat answer carries a *Demo answer, not generated by Amplifi* label. The upload screen and the "Find with Amplifi" results are marked as demo too. Mock answers are never shown as real AI output.

**Live mode** calls the platform REST API and a server-side Amplifi proxy. See [Connecting to Amplifi](#connecting-to-amplifi).

## Configuration

Copy `.env.example` to `.env.local` and edit. All variables are read once at startup in `src/services/config.ts`, and invalid values fall back to safe defaults.

| Variable | Default | Purpose |
| --- | --- | --- |
| `VITE_DATA_MODE` | `mock` | `mock` or `live` |
| `VITE_PLATFORM_API_BASE` | `/api` | Base URL of the platform REST API |
| `VITE_AMPLIFI_PROXY_URL` | `/amplifi` | Base URL of the server-side Amplifi proxy |
| `VITE_REQUEST_TIMEOUT_MS` | `30000` | Timeout per request; uploads get four times this |
| `VITE_MAX_UPLOAD_MB` | `50` | Largest PDF the upload screen accepts |
| `VITE_ROUTER_MODE` | `browser` | `browser` (needs the server to rewrite unknown paths to `index.html`), `hash` (static hosting with no rewrites), or `memory` (embedded demos) |

Every `VITE_` variable is compiled into the JavaScript bundle and is visible to anyone using the app. **Never put tokens, API keys or other secrets in them.**

During development, set `DEV_API_TARGET=http://localhost:8080 npm run dev` to proxy `/api` and `/amplifi` to a local backend through Vite. That avoids CORS and keeps credentials on the server.

## Connecting to Amplifi

> **Status: Amplifi's API has not been verified.** No Amplifi repository, API documentation or authentication details were available when this frontend was built. The prototype referred to an `INTEGRATION.md` that wasn't supplied, and its Amplifi adapter guessed both the request body and the response fields. This frontend deliberately does **not** call Amplifi directly or invent its endpoints.

The browser talks only to a **server-side proxy** with a small contract that this frontend defines. The proxy holds the Amplifi credentials and translates requests onto Amplifi's real API. This also covers the prototype's own guidance to add credentials on the proxy rather than in the browser.

To connect:

1. Build the proxy endpoints in [docs/INTEGRATION.md](docs/INTEGRATION.md) against Amplifi's real API once its contract is confirmed. They are `POST /chat` and `POST /find-value`, plus the platform endpoints for papers, records, review and upload.
2. Set `VITE_DATA_MODE=live` and point the two base URLs at the proxy and the platform API.
3. Run the app and check each workflow. Requests that fail are explained in the UI: sign-in expired, no access, timeout, server error, or a response in an unexpected format.

Only `src/services/` needs to change if the contract has to be adjusted. Components never call `fetch` themselves.

### Open integration questions

These need answers from the Amplifi and platform owners. Each has a clearly marked place in the code.

- **Authentication.** Does the proxy use the user's session cookie (the frontend sends `credentials: "same-origin"`), or does the browser need a token from an identity provider?
- **Streaming.** The chat UI supports streamed text via the `onText` callback. The live adapter currently expects a single JSON response. If Amplifi streams (SSE or chunked), only `createHttpAmplifiClient` changes.
- **Scoping questions to one paper.** The frontend sends `scope: "CP07"`. The proxy decides whether Amplifi can filter by document ID or needs a prompt instruction, which is what the prototype did.
- **Ingestion status.** After an upload, the platform API reports only that the file was accepted. The upload card says processing status isn't reported. A status endpoint (or a webhook and polling) would let it show the real steps.
- **Answer feedback.** Thumbs up and down are recorded for the session only. There is no known endpoint to send them to.
- **Conversation history.** The frontend sends the last ten completed turns and any `conversationId` the proxy returns. Confirm which of the two Amplifi needs.

## Architecture

```
src/
  types/          Typed models: research records, papers, review items, chat, uploads
  data/           Sample data and static configuration (mock data is used only by mock adapters)
  domain/         Pure business logic, with no React: filters, chart maths, review rules, validation
  services/       Backend layer: HTTP client, response validation, mock and live adapters
  state/          React context providers: data, view state, chat, uploads, dialogs, toasts
  hooks/          Small reusable hooks (theme, media queries, stored state, page title)
  components/     Presentational components, grouped by area
    common/  layout/  navigation/  charts/  tables/  chat/  upload/  review/  detail/
  pages/          One folder per route, composing components with state
  styles/         Design tokens (variables.css) and global base styles
  test/           Test setup and app-level flow tests
```

**Data flow.** A page reads from a provider (`useResearchData`, `useChat`, and so on). The provider calls a service, and the service calls an adapter chosen once in `services/index.ts` from the config. Tests inject their own adapters through `ServicesProvider`, which is how failures and slow responses are tested without a network.

**State.** React state and context only; no state library was needed. Server data lives in `ResearchDataProvider`, which uses a reducer. Filters and selections live in `ViewStateProvider`, so they survive moving between pages. The chat thread is kept in `sessionStorage` for the current tab. Uploads live above the routes, so they keep going when the person leaves the Upload page.

**Charts.** These are hand-written SVG components rather than a charting library. The prototype's charts do Pareto ("best balance") outlines, collision-free point labels, log axes, and keyboard-focusable points that open the record. Rebuilding that in Recharts would have meant more code and about 100 KB more JavaScript. The maths is in `domain/charts.ts` and is unit tested. Records missing a value are left out and counted in the caption, never estimated.

**Styling.** Component CSS Modules on top of a token file. Colours, type and spacing come from the prototype, with the contrast fixes below. Light and dark themes follow the system until the person picks one.

**Dependencies.** At runtime: React, React DOM, React Router and Lucide icons. Everything else is development tooling.

## Accessibility

- Every page was audited with axe-core (WCAG 2 A and AA plus best practices) in light and dark themes, and again with a dialog open, a chat answer showing and an upload in progress. All pass.
- Keyboard: a skip link, visible focus on every control, and arrow-key tabs (Home and End too). Chart points and bars can be focused and opened. Enter sends a chat message and Shift+Enter adds a line. Dialogs trap focus, close on Escape and return focus to where they were opened. The file input stays focusable.
- Screen readers: tables are real tables with captions; on phones they restack visually. Status messages, toasts and streaming answers use live regions. Icon buttons have names, and the review badge is announced as "6 waiting".
- Contrast fixes over the prototype: muted text, the brand button teal, the approve-button green, the checked-status green and the link teal were all below 4.5:1 and have been darkened slightly to pass.
- Reduced-motion preferences turn off animation.

## Testing

`npm test` runs 69 tests.

- **Domain:** pair filtering and summaries, compare picks, the untested grid, chart maths (ticks, log axes, Pareto front, correlation, missing values, label placement), review state changes, PDF validation, citations and formulae.
- **Services:** HTTP error mapping (401, 403, 404, 413, 5xx, network, timeout, cancellation, invalid JSON), response validation, the proxy contract (including checking that no credentials are sent from the browser), and mock streaming and stop.
- **Flows, rendering the whole app:**
  - Dashboard links and quick questions.
  - Find with Amplifi on a missing value.
  - A failed load with retry.
  - Library search and filters that persist.
  - Review: approve, correct with validation, failed save, and double-click protection.
  - Upload: rejection, the full pipeline into the Library, failure and retry.
  - Chat: demo labelling and citations, the error state, follow-up history and scope, and opening the chat from a paper.

## Known limitations

- Fonts load from Google Fonts. For locked-down government networks, self-host Montserrat (for example with `@fontsource/montserrat`) and remove the link in `index.html`.
- In mock mode, review decisions and uploads last only until the page is reloaded.
- The live HTTP adapters have been tested against the documented contract with stubbed responses, not against a running backend.
