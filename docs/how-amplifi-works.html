How Amplifi works

What the Amplifi platform does, how its parts fit together, and where each part lives in the code. It is written so anyone on the Battery POC team can follow it and explain it.

Date 26 October 2026 Based on the amplifi-dev repository: README, CLAUDE.md, the user docs in docusaurus/docs and the service READMEs, checked against the code Scope read-only; nothing in Amplifi was changed

Amplifi in one sentence

Amplifi takes an organisation's documents and data, makes them searchable by meaning, and lets AI agents answer questions about them while showing the passages they used. It is built by ThoughtsWin Systems and runs on Microsoft Azure.

Three things to remember

  1. Everything lives inside a workspace. Files are grouped into datasets, datasets are searched by tools, and tools are used by agents.
  2. Slow work, like reading 30 PDFs, is done by separate worker services that pick jobs off a queue. The API itself always answers quickly.
  3. An agent is a prompt + a language model + search tools. It searches first, reads what it found, then writes the answer.

The big picture3 / 10

The big picture: every part on one page

Amplifi is not one program. It is a set of cooperating services, each running in its own container. Requests come in at the top; slow work is passed down to workers; everything ends up stored in Postgres.

Entry pointsAmplifi's own servicesStorageExternal AI service
fastapi-serviceThe only part that speaks HTTP. It checks logins, reads and writes records, runs agents for chat, and puts slow jobs on a queue.
RabbitMQA post office for jobs. Each kind of job has its own named queue, and the matching worker collects from it.
Worker servicesSeparate programs, each doing one kind of job: reading documents, transcribing audio, building graphs, training SQL models. Built on Celery.
Postgres + pgvectorThe main database: users, workspaces, datasets, agents, chat history, job results, and every chunk with its embedding.
Memgraph and RedisMemgraph stores knowledge graphs. Redis is a short-term memory, for example a login that was just checked.
Azure OpenAIWrites answers, makes embeddings and tidies questions. Amplifi's rules keep customer data in region.

Also running: nginx allows 10 requests a second per caller; Temporal runs long workflows that must survive crashes; Vault holds secrets; Flower, Prometheus and Grafana monitor it all. Older diagram: static/hld_view_Amplifi.png shows an earlier design with an "R2R server" doing search. The current code does that itself.

Journey 14 / 10

Journey 1: getting documents in

Before anyone can ask a question, files must be ingested. The first four steps happen through the API, from the web app or another program. The API then hands the heavy work to a worker, so the screen does not freeze while 30 PDFs are read.

Done through the APIDone by a background worker

What chunking with overlap looks like

The web app's default is 2,500 characters per chunk with 250 characters of overlap, roughly half a PDF page. The overlap means a sentence cut at a boundary still appears whole in one chunk. The user docs describe the size in tokens (about 2.5 pages), but the setting the code sends is max_characters.

Journey 25 / 10

Journey 2: asking a question

A question goes to an agent. The agent does not answer from memory. It runs a loop: the language model decides what to search for, a tool does the search, the model reads the results, and it repeats until it has enough to answer.

Three ways to send a question

RouteWho can call itWhat comes back
POST /chat/uploadPeople and API clientsOne JSON reply with no history. An optional output_schema forces the answer into a fixed JSON shape. PDFs or images can be attached.
POST /chatSigned-in peopleOne JSON reply, saved to a chat session so follow-up questions keep their context
POST /chat/streamSigned-in peopleThe same reply, streamed word by word while it is written

Details that surprise people

The question may be rewritten. Before the agent starts, GPT-4.1 checks whether the message holds several questions. If it does, the agent answers each part separately and the reply has one entry per part.

History is short. The model sees only the last 5 messages of a session.

 

Sources are chunks, not pages. The reply lists the chunks the tools returned. Page numbers in an answer come from the model reading the text, so they need checking.

Errors can look like success. If the agent fails, /chat/upload still returns HTTP 200 with an error field.

Search6 / 10

How search finds the right passage

Every chunk's embedding places it on a "map of meaning". Passages about similar things land close together, even when they use different words. A question is placed on the same map, and search returns the chunks nearest to it.

Example question: "What is the reversible capacity of BGP@HEC-HC?" Nearness is measured with cosine distance by default; L2 and Lp distances can be chosen on the Search page, which also reports precision, ranking quality (NDCG) and speed per dataset.

Find the file first, then search inside it. When an agent has both File Navigator and a search tool, Amplifi tells it to locate the file before searching. The Theme B tools follow that order: Tool-01 File Navigator, Tool-02 Vector Search, then Tool-03 Hybrid Search.

More features7 / 10

Knowledge graphs, SQL and other features

Knowledge graphs: facts as connected dots

A knowledge graph is built from an ingested dataset in two passes: first the entities (materials, papers, people, organisations), then the relationships between them. graph-service does the work and stores the result in Memgraph. Graph Search then lets an agent follow the links, which suits questions about connections.

Illustrative example drawn from the POC's papers; it is not an actual graph from Amplifi.

Text to SQL: questions about tables

For data that lives in a database, ingestion does not chunk anything. Instead training-service trains a Vanna model on the table layout, some written notes and example question-and-SQL pairs. The Text to SQL tool then turns a plain question into SQL, runs it and returns a table.

Data sources

Files can be uploaded directly, or pulled from Azure Blob Storage, AWS S3, Groove tickets and databases (Postgres, MySQL, Redshift, Microsoft Fabric). monitoring-service checks Azure and Groove for new files on a timetable kept by celery-beat-service.

Destinations and workflows

A workflow copies a dataset's vectors to another store, such as PG Vector or Databricks Vector Search, daily, weekly or monthly.

MCP tools

MCP (Model Context Protocol) lets an agent use tools that live outside Amplifi, such as a company search API. Tavily web search comes built in.

Extraction

A newer feature that pulls structured fields out of documents. It runs on Temporal in extraction-worker, so a crash resumes where it stopped. A setting switches it on.

How one job travels. The API never does slow work itself. It writes a job onto a named queue in RabbitMQ and replies at once. The worker for that queue picks the job up, does the work and writes the result to Postgres. The app checks the status later. Locally, the Flower page at localhost:5555 shows every queue and worker.

How the backend code is written

Python 3.12, with uv managing packages. Each service is a container image. Services never import each other; they share code only through packages/, all imported under one name, shared.*.

Settings come from environment variables in a .env file, which holds real secrets and is never committed.

The shared packages, from bottom layer to top

Arrows mean "uses". A package may only use the layers to its left. Newer packages for extraction, page layout and vision sit alongside these.

What this means for the Battery POC

  • BRP does not change Amplifi. It calls one route, POST /api/v3/chat/upload, through a small server-side proxy that holds the API client secret.
  • Papers, datasets, tools and agents keep being managed in the Amplifi web app.
  • output_schema can force the JSON shapes BRP's screens need.
  • Open points, such as question splitting, page numbers and timeouts, are listed in docs/amplifi-api-notes.md.
